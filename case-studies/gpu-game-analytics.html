THE QUESTION 先判斷 workload fit

不是「GPU 快幾倍？」而是「計算夠大、路徑夠原生嗎？」

3 個營運分析情境同一 Colab T4 環境

PRODUCT FRAMING

從「搬上 GPU」改成「逐段證明值得搬」

資料團隊若直接把 pandas 分析交給 GPU 相容層，部分操作可能仍回到 CPU；小型結果也未必能攤平啟動與資料傳輸成本。

工作負載不一樣

RFM、cohort 留存和付費漏斗的操作型態不同，不該把一個 benchmark 結論套到整條分析流程。

相容不等於原生

`cudf.pandas` 讓既有程式先行試跑，但部分操作會 fallback；必須追查實際計算路徑。

PM 需要可行動的結論

不只比較秒數，還要說明何時先留在 CPU、何時值得改寫、如何用同機重測。

MEASURED EVIDENCE

20M 筆資料：GPU 並沒有每次勝出

公開 notebook 記錄同一 Colab T4 環境中的 pandas CPU baseline 與 `cudf.pandas` GPU run。秒數愈短愈好；此處呈現的是分析步驟的量測值，不是端到端服務 SLA。

關鍵洞察：工作量大、而且運算能留在原生 GPU 路徑，才有機會抵銷 GPU 啟動與搬移成本。相容層並不代表每個 operation 都在 GPU 上執行。

WHY IT HAPPENS

把「較慢」拆成可處理的原因

RFM：fallback 與資料搬移

`qcut`、`rank`、`np.select` 等操作可能離開 GPU 原生路徑，CPU 計算及 host/device 間的搬移成本會抵銷收益。

留存：結果太小

`nunique` 可用 GPU，但這個情境只產生約 90 個群組；小輸出可能難以攤平 kernel launch 與搬移開銷。

漏斗：Python 物件邊界

以 Python `set` 做交集會讓結果回到 host 端 Python 物件，GPU 難以持續承擔主要計算。

下一步：原生改寫，再同機量測

可以嘗試以 GPU-native groupby、merge、sort 等路徑重寫；但改寫本身不等於已證明變快，仍要跑同一資料與硬體的對照。

PRODUCT JOURNEY

由 benchmark 走到 GPU-fit 決策

Lab 將工程量測轉成 PM 與分析工程師可以討論的下一步，不把「GPU」當成預設答案。

選擇分析情境

以 RFM、留存、漏斗切入常見遊戲營運問題。

閱讀已記錄證據

同列比較 CPU 與 cuDF 執行時間，辨識 fallback 線索。

取得初步建議

fallback-heavy／小輸出情境先留在 CPU，或先考慮原生改寫。

回到 Colab 驗證

在自己的 runtime 重跑，才決定是否將工作負載交給 GPU。

Lab 的邊界：Hugging Face Space 是靜態展示，呈現已紀錄測值與 deterministic 決策規則；它不會在頁面內執行 cuDF 或產生新的 GPU benchmark。

SCOPE & NEXT

可驗證的結論，以及尚未宣稱的部分

目前可支持

  • 20M 合成事件中，RFM 與留存的已記錄 cuDF pandas run 較慢；Python-set 漏斗接近持平。
  • 公開 notebook 可用於 Colab T4 重跑並檢視計時流程。
  • GPU-fit Lab 將 workload 特徵與下一步建議做成互動說明。

目前不宣稱

50M native sort/groupby/merge 尚未公開完整成對 CPU/GPU 數字；不宣稱它已加速。合成資料與單一 Colab T4 環境也不能代表客戶系統、正式 SLA、成本節省或 ROI。
